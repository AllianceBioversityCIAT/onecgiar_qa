## 2. Executive Summary

The whole change rests on one fact. The current rules already compare **lexically ordered Rome strings**: `YYYY-MM-DD` against "today". If step boundaries become `YYYY-MM-DDTHH:mm` minutes and "today" becomes **the current Rome minute**, then every comparison keeps its shape, and S-2 (the closing minute is included) falls out of the same comparisons the code uses for days:

| | Today (days) | New (minutes) |
|---|---|---|
| `in_progress` | `opensOn ≤ today ≤ closesOn` | `opensAt ≤ nowMinute ≤ closesAt` |
| `closed` | `closesOn < today` | `closesAt < nowMinute` |
| Overlap | `opensOn ≤ previous closesOn` | `opensAt ≤ previous closesAt` |
| Close before open | `closesOn < opensOn` | `closesAt ≤ opensAt` (now strict, FR-3) |

So the design is mostly a **widening**:

- a branded `RomeMinute` type, so a day and a minute can never be compared by mistake;
- `nowInRome` replaces `todayInRome`;
- the step columns become `DATETIME`, read and written through a custom column type;
- a thin compatibility layer at the API edge keeps `opensOn` / `closesOn` (FR-9).

There is no new module, no new table and no new route.

## 3. Architecture Overview

All changes stay inside the existing `admin-config` module and the `timeline_steps` table (TRD § 4, module per domain). Data flow is unchanged:

`TimelinesController` → `TimelinesService` (reads `ADMIN_CONFIG_CLOCK` once per request) → pure rules (`timeline-rules.ts`, `timeline-view.ts`, `field-config-versions.ts`) → stores (Drizzle).

The only new idea is the time source:

- The clock still returns an instant (`Date`).
- `nowInRome(instant)` turns it into the current Rome minute, using the single zone constant (FR-10).
- Pure functions receive that `RomeMinute`. They never read a clock and never see a zone (NFR-1).

## 5. Data Model

**Table `timeline_steps`.** Migration `0006_timeline_step_times`:

| Column | Before | After |
|---|---|---|
| `opens_on` | `DATE NOT NULL` | renamed `opens_at`, `DATETIME NOT NULL` (seconds always `00`) |
| `closes_on` | `DATE NOT NULL` | renamed `closes_at`, `DATETIME NOT NULL` (seconds always `00`) |
| `chk_timeline_steps_dates` | `closes_on >= opens_on` | `closes_at > opens_at` (same name) |

**Migration order** (one custom SQL file, DD-6):

1. Drop the check.
2. Rename and change the type of both columns. Existing values become `… 00:00:00`.
3. Set `closes_at` to `… 23:59:00` on every row (S-6, FR-11).
4. Add the check back, strict.

**Down script** (manual, NFR-3), in reverse order: drop the check, change both columns back to `DATE` (dropping the time), rename them back, add the old check. The rollback is lossy only for times that differ from 00:00 / 23:59, and is documented as such.

**Value format.** The database holds `YYYY-MM-DD HH:mm:00`. A custom Drizzle column type maps it to and from `RomeMinute` (`YYYY-MM-DDTHH:mm`), so stores and rules never see the database form (DD-3). DATETIME carries no zone: what is stored is Rome wall-clock time (S-7).

**Not changed:** `timeline_audit_events` (FR-12 changes only the keys written from now on), `cycles`, and the `field_config_*` tables (`published_at` stays an instant).

## 6. API Design

No route is added or removed. These shapes change:

| Method | Path | Roles | Request change | Response change | New errors |
|---|---|---|---|---|---|
| POST | `/cycles/:id/timelines` | ADMIN | `steps[i].opensAt` and `closesAt` (`YYYY-MM-DDTHH:mm`). `opensOn` and `closesOn` are still accepted per field (FR-9) | Timeline (below) | `DST_HOUR`; `INVALID` when both forms are sent |
| PATCH | `/timelines/:id` | ADMIN | Same, per sent field | Timeline | same |
| GET | `/cycles/:id/timelines`, `/timelines/:id` | ADMIN | — | Timeline | — |
| GET | `/cycles`, `/cycles/:id` | ADMIN | — | none (`startsOn` / `endsOn` stay days, FR-13) | — |

**Timeline response:**

- adds `timeZone: "Europe/Rome"`;
- each step adds `opensAt` and `closesAt`, and keeps `opensOn` / `closesOn` as their date part.

**Field error paths.** An error names the key the client actually sent, so an old client that sent `steps[0].opensOn` still gets `steps[0].opensOn` (DD-5). Rule errors on a moment that came from a day-only key are reported on that day-only key.

**Codes:**

| Code | Status | |
|---|---|---|
| `DST_HOUR` | new | Message: "This time does not exist or happens twice in Rome on this day (daylight-saving change). Choose another time." |
| `BEFORE_TODAY` | same code | Now judged to the minute; the message "This date cannot be in the past." still fits |
| `CLOSES_BEFORE_OPENS` | same code | Now also covers the same moment |

## 7. Backend Module Design

### 7.1 Time helpers (`rome-date.ts`)

| Element | Responsibility | Requirement |
|---|---|---|
| `QA_TIME_ZONE` | The only `'Europe/Rome'` in `server/src`. The two `Intl` formatters (day and minute) and the response's `timeZone` read it | FR-10, NFR-2 |
| `RomeMinute` (branded string) | `YYYY-MM-DDTHH:mm`. Built only by the helpers below, so passing a `YYYY-MM-DD` where a minute is expected fails the build | Defect class "day vs moment" |
| `isRomeMinute(text)` | Exact shape, a real calendar date, hour 00–23, minute 00–59 | FR-1 |
| `nowInRome(instant)` | The Rome wall-clock minute of an instant (seconds dropped) | FR-2, FR-7 |
| `dayStart(day)` / `dayEnd(day)` | `T00:00` / `T23:59` of a day-only date | FR-9, FR-11, S-6 |
| `dayOf(minute)` | The date part | FR-9, FR-13 |
| `isDstHour(minute)` | True when the minute is 02:00–02:59 on a day whose Rome UTC offset at the start differs from the offset at the end. Read from `Intl`, never from a hand-written "last Sunday" rule (DD-4) | FR-4 |
| `compareDates` | Unchanged for days. Minutes compare through a typed variant | — |

`todayInRome` is removed once no caller remains (callers listed in P-6).

**Why seconds can be dropped.** A boundary is a whole minute (S-2), so `now` falls inside a step's window exactly when its minute does:

- 13:59:59 has minute 13:59, which is before 14:00: `upcoming`.
- 17:30:59 has minute 17:30, which is not after 17:30: `in_progress`.

The same holds for the publish instant in FR-8: published at 14:00:10 gives minute 14:00, which is not before 14:00, so the version does not count.

### 7.2 Reading a moment from a request (`timeline-rules.ts`)

One reader per boundary (open, close) of each sent step, replacing `readDate`:

| Input for one boundary | Result | Field reported |
|---|---|---|
| Only `…At` | Checked with `isRomeMinute`, then `isDstHour` | `…At` |
| Only `…On` (day-only) | Checked as a calendar date; it becomes `dayStart` or `dayEnd` (open or close); then `isDstHour` (never true for 00:00 / 23:59) | `…On` |
| Both | `INVALID` | `…On` (FR-9) |
| Neither, on create | `REQUIRED` | the request's family (below) |
| Neither, on edit | Keeps the stored value | the request's family (below) |

The reader remembers which key was used, and every later rule on that boundary reports on that key (DD-5). A boundary the request did not send (missing on create, stored on edit) is named on `…On` when the request sent only day-only keys, else on `…At` (DD-5). *Amended 2026-10-27 (T-4 spec tension, approved by the back lead).*

Then the rules run unchanged in structure, with minutes:

| Rule | Code | Requirement |
|---|---|---|
| `closesAt ≤ opensAt` | `CLOSES_BEFORE_OPENS` | FR-3 |
| `opensAt ≤ previous closesAt` | `OVERLAPS_PREVIOUS_STEP` | FR-3 |
| Create, step 1 `opensAt < nowMinute` | `BEFORE_TODAY` | FR-5 |
| Edit locks by state | `LOCKED` / `BEFORE_TODAY` | FR-6 |

Edit locks use the state from 7.3 and `nowMinute`.

**What counts as unchanged on edit.** A boundary is unchanged when its **normalized moment** equals the stored one. So a day-only `closesOn` equal to the stored date, over a stored `17:30`, is a change to `23:59` (FR-9, last scenario).

The context's `today: string` becomes `now: RomeMinute` throughout `TimelineRulesContext`.

### 7.3 Status, step state, hold (`timeline-view.ts`)

`TimelineViewInput.today` becomes `now: RomeMinute`, and the step fields become `opensAt` / `closesAt`. The decision table is the current one (`timeline-view.ts:66-105`) with minutes in place of days (FR-7). The hold, the scope lock (*edit* FR-4) and the in-progress confirmation (*edit* S-8, `timelines.service.ts:508`) all read this same state, so they move together.

### 7.4 Service (`timelines.service.ts`)

- The three `todayInRome(now)` call sites become `nowInRome(now)` (P-6).
- The instant used to judge an edit is still the one its answer is read at (*edit* NFR-4). Nothing else changes.

### 7.5 Field-configuration start (`field-config-versions.ts`, `field-config.store.ts`)

- `TimelineStart` carries `opensAt` / `closesAt` (`RomeMinute`).
- **Started:** `opensAt ≤ nowMinute`.
- **Finished:** started, and `nowMinute > last closesAt`.
- **A version counts** when `nowInRome(publishedAt) < opensAt` (FR-8).
- `listTimelineStarts` selects the renamed columns. Its "latest close" reduction compares minutes. The statement count stays three (`field-config.store.ts:94`).

### 7.6 Cycle span (`cycles.store.ts`)

`min(opens_at)` and `max(closes_at)` return DATETIME strings. The store maps them to `dayOf`, so `startsOn` / `endsOn` keep their shape (FR-13).

### 7.7 Response, DTOs, OpenAPI, audit

- **Response mapper:** `opensAt` and `closesAt` as stored; `opensOn` / `closesOn` = `dayOf`; `timeZone` = `QA_TIME_ZONE`.
- **DTOs:** the four keys are optional strings. Validation of presence and shape stays in the rules, so that every problem is reported in one 400 (*timelines* FR-11).
- **OpenAPI:** the models document all four keys plus `timeZone`, with examples. The day-only keys are marked deprecated.
- **Audit diff:** `steps.<position>.opensAt` / `closesAt`, with minute values (FR-12).

### 7.8 Error catalog

Add `DST_HOUR` with its message (§ 6). Update the module guides with the new rules and the `0006` note.

## 10. Design Decisions

| ID | Decision | Alternatives rejected | Consequence | Requirements |
|---|---|---|---|---|
| DD-1 | **Rome wall-clock minutes as strings**, compared lexically against `nowInRome` | UTC instants (rejected by the back lead); separate `TIME` columns (two sources for one fact) | Rules keep their shape; no zone in the database; a future zone change needs a data migration (accepted) | S-7, FR-1, FR-2 |
| DD-2 | **Minute granularity everywhere**: `now` is truncated to its minute before any comparison | Second-precision `now` against `HH:mm:59` bounds | One comparison per rule; S-2 holds by construction (§ 7.1) | FR-2, FR-7, FR-8 |
| DD-3 | **Branded `RomeMinute` type, plus a custom column type** that converts between the database form and `YYYY-MM-DDTHH:mm` | Plain `string` with a format convention | Mixing a day with a minute fails the build (compile gate); the stores never format strings by hand | FR-1, defect class "day vs moment" |
| DD-4 | **DST hours found through `Intl`**: the offset at the start of the day differs from the offset at its end | Hand-coded "last Sunday of March / October" | Follows tzdata if the EU rule changes; no table to maintain | FR-4 |
| DD-5 | **An error names the key the client sent** (`…On` or `…At`) | Always `…At` | The current front keeps mapping its errors without a change (consumer P-8) | FR-9 |
| DD-6 | **One migration `0006` whose snapshot and journal entry come from an interactive `drizzle-kit generate` run by a human (answering "rename" for both columns), and whose SQL body is then replaced by the reviewed four-step SQL of § 5**, plus a manual down script. Amended 2026-10-27 (Pivot T-3: P-3 false) | `--custom` (its snapshot copies the previous schema, P-3); a hand-edited snapshot; three migrations (add, backfill, drop) | One reviewed SQL file; a human applies it (`server/src/database/AGENTS.md:49-50`) | FR-11, NFR-3 |
| DD-7 | **Additive API**: `…On` kept as a derived value and accepted on write (meaning 00:00 / 23:59). Both forms in one field is `INVALID` | Breaking rename | Old and new fronts work; clean-up later | FR-9 |
| DD-8 | **`timeZone` on every timeline**, read from the same constant the rules use | A config endpoint; an env var | No new route; one source (NFR-2) | FR-10 |
| DD-9 | **The cycle span stays in days** (`dayOf` of min/max) | Expose moments | `cycles` contract untouched | FR-13 |

**Reversion challenge (Step 2.3).** Two behaviors that ship today are removed:

| Removed behavior | Rule | What does removing it break? | Answer |
|---|---|---|---|
| "Two steps never share a day" | *timelines* S-1 | The front shows a step's day range on its cards. Two steps on the same day would now show the same day | Not a breakage of the server contract. The front must show the times (AC 2), recorded in `front-contract.md`. Kept |
| "A step may open and close on the same day" | *timelines* FR-8 | Still true: same day, different minutes. Only the same *minute* is refused | Nothing breaks. Kept |
