# src/users — Agent Guide

Users, roles, role assignments, program scope, permission evaluation and the **admin API** (`/users`, `/catalogs`). Specs: `docs/specs/auth/cognito-native-session/` (DD-1, § 7.1) and `docs/specs/auth/user-management/core/` (FR-1…FR-14, DD-1…DD-15). Other modules import `UsersModule` for `AuthorizationService` and the repositories — never the Drizzle stores directly. Root and `server/AGENTS.md` rules apply.

## Rules

- **Permissions are data, not code paths.** A new capability is a new `Permission` member plus the roles that grant it in `ROLE_DEFINITIONS`. Never write `if (user.role === 'ADMIN')`; call `can()` / `canAny()`. ADMIN grants **every** permission, derived from the catalog (DD-10): a new permission reaches ADMIN with no edit, and the matrix test changes.
- **Scope:** `global` roles have no scope key; `result_type` roles need a result type key or `'*'` = all result types, current and future (DD-1); `program` roles need a program id. `READ` is the marker every authenticated user holds (GUEST included). LEAD_ASSESSOR also grants the assessor permission within the same result type.
- **Assessor/Lead exclusivity (DD-2, DD-11):** ASSESSOR and LEAD_ASSESSOR on overlapping result types (`*` overlaps everything) are forbidden for one user. The check lives in `RoleAssignmentsRepository` over the user's resulting active grants, under the user row lock, so every writer (service, seed) obeys it.
- **Effective scope (DD-13):** `canReview` = permission for the result type (exact key or `*`) **and** program in scope (no rows = all) **and** no active exclusion. An active ADMIN is exempt from the scope and exclusion conjuncts only; the permission check and any later timeline predicate still apply. Exclusions of an admin stay stored.
- **Live grants only:** a grant counts only while it is live (`isLiveAssignment`: active, not revoked, role active and in the catalog). The SQL counterparts — the list's counts and filters in `users-query.repository.ts`, the last-admin count in `users-admin.unit-of-work.ts` — must apply the same condition; a revoked or inactive-role row never counts.
- **Resource checks (DD-4):** the route guard only checks `canAny`. A handler that loads a scoped resource must then call `can(user, p, { resultType | programId })` (or `canReview`) itself — reviewers check this.
- **Writes go through the repositories,** which hold the rules the database cannot (scope vs role, exclusivity). Do not insert into `role_assignments` directly.
- **Admin mutations go through `UsersAdminService` only** and run in `USERS_ADMIN_UNIT_OF_WORK`. Lock order (DD-14, design 7): target `users` row `FOR UPDATE` → ADMIN `roles` row `FOR UPDATE` (only when admins can decrease; the last-admin guard runs **before** any grant insert, whose foreign key takes a shared lock on `roles`) → `role_assignments` writes → program-scope and exclusion rows `FOR UPDATE` (`replaceUser` runs edit, roles, programs, exclusions in that order, so the exclusion locks of `reconcileExclusions` come last of the user-data locks). A keyed mutation then takes a final X lock on its `idempotency_keys` row in `markExecuted` (called from `users-admin.service.ts`, inside the unit of work); the out-of-tx `takeOver` and `complete` also touch that row, outside any user-data lock. The transaction is `READ COMMITTED`: the last-admin count is a plain read taken after the `roles` lock; uniqueness pre-checks are plain reads and a race is caught by the unique index (DD-15). Logins keep the auth order (`users` → `role_assignments` → `roles`, shared locks only).
- **Audit granularity (DD-15, FR-13):** an edit request = one `update` row holding every changed field (`{ field: { before, after } }`); each role grant or revoke, scope change, exclusion add/remove/dismiss, deactivation, reactivation and invitation resend = its own row; a create = one `create` row plus those rows. A refused or rolled-back request writes none. `test/users-admin-privacy.e2e-spec.ts` pins the counts over HTTP.
- **Cache freshness (FR-11, FR-6):** any write that changes a user, their assignments, scope or exclusions calls `CurrentUserCache.invalidate(userId)` **after** the commit. Other processes see it within 60 s.
- **Idempotency (FR-1…FR-9):** a keyed request carries its reservation in `AdminContext`; every mutation calls `markExecuted` inside its own unit of work (zero rows affected = the lease was taken over: `IdempotencyFenceLostError`, rollback). A request without the header marks nothing. The behavior of the interceptor is in `src/common/AGENTS.md`.
- **Logging (NFR-2):** one `users_admin` decision line per mutation with fixed fields only — `event`, `action`, `targetId`, `actorId`, `outcome`, `reason?`, `requestId`, `idempotency` (`none` | `taken_over`). Never an email, name, nickname, reason text, temporary password or key. A replayed, in-flight or reused-key request never reaches the service: the interceptor writes its one `event:"idempotency"` line instead (no `users_admin` line). Otherwise a second event for the same request is not allowed: the Cognito-sent-but-not-recorded case (`reason: cognito_sent_not_recorded`) rides on the error and is folded into that one line (`FORCED_LOG_REASONS` in the service). A request the validation pipe refuses never reaches the service and logs no decision line. The log-spy e2e covers every logger and `console`.
- **FR-12 (rule for later specs):** an endpoint that is not admin-only and renders a user other than the caller shows the **nickname and id only**, built with `toPublicUser` — never the email or the full name. `/auth/me` shows the caller's own nickname.
- **Cognito:** `CognitoAdminClient` is called only from the service, before the transaction and outside any lock; a 10 s budget; failure → 503 `AUTH_SERVICE_UNAVAILABLE` and no QA row.
- **Catalogs:** validate result type keys and program ids through `CatalogService`; a stale copy is acceptable, none → 503. Never query Reporting tables.
- Adding a role or permission also needs: the seed (`src/database/seeds/seed.ts` uses `ROLE_DEFINITIONS`), the matrix test, and the spec.

## Testing

- Unit tests use the in-memory stores in `test/support/in-memory-stores.ts`; they emulate unique keys and the generated `active_key`, and count `writes` for "changes nothing" assertions. `test/support/users-admin-world.ts` builds the whole admin world (service, fake Cognito and catalogs, recording unit of work) for service specs.
- HTTP: `test/users-admin.e2e-spec.ts` (routes, shapes, errors, OpenAPI), `test/users-admin-privacy.e2e-spec.ts` (log spy over every route, audit coverage, nested unknown keys), `test/users-admin-idempotency.e2e-spec.ts` (keyed replay, reuse, in-flight, take-over, parity of `PUT /users/:id`), `test/users-admin-idempotency-privacy.e2e-spec.ts` (log spy over keyed writes), `test/catalogs.e2e-spec.ts`.
- Extend `authorization.matrix.spec.ts` for every new permission or role: every role × scope × context must have an explicit expected result.
- Drizzle adapters are verified by type-check and generated-SQL assertions; there is no disposable MySQL for tests (shared `qadb` is never reset).
