# src/admin-config — Agent Guide

Cycles and QA timelines: the admin API that says *when* QA runs, *for which* Science Programs and result types, and *who* works in each timeline. Spec (archived): `docs/specs/archive/2026-10-21-admin-config--cycle-timelines/` (`design.md`, DD-1…DD-10). What the front may rely on: `front-contract.md` in the same folder. The timeline edit (`PATCH /timelines/:id`) is spec `docs/specs/admin-config/timeline-edit/` (its `front-contract.md` is the front's source). The field configuration of a cycle (`field-config/`) is spec `docs/specs/archive/2026-10-27-admin-config--field-configuration/` (its `front-contract.md` is the front's source). Root and `server/AGENTS.md` rules apply.

## Model in one line

`cycles` → `timelines` (one official + any number of additional per cycle) → `timeline_steps` (1-5, one per audience), plus scope rows (`timeline_programs`, `timeline_result_types`) and assignments (`timeline_users`). This replaces the old `cycles → windows → batches` text of the TRD (DD-1); there is no window and no batch here.

## Rules

- **ADMIN only (FR-16).** The three controllers (`CyclesController`, `TimelinesController`, `FieldConfigController`) carry `@RequirePermission(Permission.ADMIN_ACCESS)` at class level; a new route inherits it. Adding a route without it is a review failure.
- **Dates are Rome calendar days, never instants.** `opens_on` / `closes_on` are `date` columns in string mode (DD-5) and travel as `YYYY-MM-DD`. A step is open from 00:00 of `opensOn` to 23:59:59 of `closesOn`, Rome time (S-1). Do not build a `Date` from a step date; use `rome-date.ts`.
- **Time only through `ADMIN_CONFIG_CLOCK`.** Never `new Date()` or `Date.now()` in a service or rule.
- **Status is computed on read, never stored** (DD-2): `scheduled`, `waiting_for_load`, `live`, `finished`, each step's `state` (`closed` · `in_progress` · `upcoming`), `currentStep`, `nextStep` and `readiness` come from `timeline-view.ts`. No job and no column flips a timeline.
- **Every rule problem in one 400 (FR-11).** The pipe checks shape only (types, unknown fields). Text length is **not** the pipe's: `name` and step names are trimmed and measured by the rules (`checkText`, `REQUIRED` / `TOO_LONG` at 120), so a whitespace-only name is `REQUIRED`, not a shape error. The scope lists and the step dates are optional at the pipe on purpose, so an absent one reaches `timeline-rules.ts` and is reported `REQUIRED` next to the other problems. Do not tighten those DTO fields: it splits the answer into two rounds. Field paths on **create** are the request keys (`name`, `programIds`, `resultTypeKeys`, `steps[i].<key>`, `i` the request index). On **edit** a step problem is `steps[position - 1].<key>` (`stepPath`: the step's place in the timeline, not in the request); the only request-index path is a bad `position` itself (`steps[i].position`, `INVALID`: unknown or repeated position).
- **Explicit "all" (DD-6).** `allPrograms` / `allResultTypes` are flags; an empty or absent list never means "all". Flag false needs at least one id; flag true needs none (a non-empty list with the flag true is `INVALID`). Catalogs are read (through `CatalogService` from `UsersModule`) only for explicit lists, so an "all" create works while CLARISA or Reporting is down; an unreachable catalog is 503 `SERVICE_UNAVAILABLE`.
- **Kind is the server's call (DD-3).** `kind` is not in the body (an unknown field is 400). Official vs additional is decided under `FOR UPDATE` on the cycle row; `uq_timelines_official_key` is only the backstop.
- **Lock order (DD-9):** cycle row → timeline → assignment rows for writes; readers never lock. The edit takes the cycle `FOR SHARE`, then the timeline `FOR UPDATE` (version re-checked), then a conditional `UPDATE ... WHERE id = ? AND version = ?` (`updateTimeline`: the database decides a race; 0 rows = stale). Create/assign/remove lock the cycle (`FOR UPDATE` to create, `FOR SHARE` to assign or remove). Activation locks the target `FOR UPDATE`, then the active row `FOR UPDATE`, closes it, then activates the target.
- **Activation retry (design 7.3 as amended 2026-10-21).** With no active cycle there is no row to lock, so concurrent activations race on `uq_cycles_active_key`: a loser gets MySQL 1062 on that key (named in the driver message) or 1213 deadlock, rolls back fully and starts over, up to 10 attempts in total (`ACTIVATION_ATTEMPTS = 10` in `cycles.service.ts`; one retry was not enough on TEST with 5 concurrent activations). A retry closes the winner's cycle (different target) or answers 409 `CYCLES_NOT_DRAFT` (same target). If every attempt is refused it answers 503 `SERVICE_UNAVAILABLE` (`CycleActivationBusyError`, retryable, nothing committed), never 500. A 1062 on another key or any other error is not retried. One decision line per request, whatever the attempts. Never two active cycles; never a reader that sees none while one exists.
- **Assignments (FR-14, FR-15).** Only ASSESSOR, LEAD_ASSESSOR, TPB, PPU are assignable (a pipe check). The user must be active and hold a **live** grant of that role (`isLiveAssignment`, the same condition as `src/users/AGENTS.md`), else 409 `TIMELINES_USER_NOT_ELIGIBLE`. A repeat assign hits `uq_timeline_users_active_key` and answers the existing row with 200, not 409 (DD-10). Remove keeps the row (`removed_at` / `removed_by`); re-assigning later makes a new row. A revoked grant does **not** delete assignments: the visibility rule (P2-3909) re-checks the live grant, so a stale row grants nothing.
- **Edit flow (`TimelinesService.update`, FR-1 to FR-14).** Partial body: a key left out keeps its stored value; `version` is the only required key; the structure is fixed (an unknown key at any level, or `audience` / `round` / `requiresLoad` / `kind`, is 400 `UNKNOWN_FIELD`). `null` is only tolerated on `programIds`, `resultTypeKeys`, `opensOn`, `closesOn` (lists: "left out"; dates: `REQUIRED`, plus `LOCKED` on the same field when that date is locked, since `null` differs from the stored day: `timeline-rules.ts:548-553` and `readDate`). Any other `null` is the pipe's 400 `REQUIRED` on that key, **not** `INVALID_TYPE`: `toFieldErrors` reads every `null` as missing (`src/common/validation.ts:43-51`; `update-timeline.dto.spec.ts:64-68` checks only the field, not the code). Answer order, first that applies wins: 404, closed cycle 409, **stale 409**, catalog 503, **every rule problem in one 400**, **in-progress confirmation 409**, no-op 200, then the write. Everything before the write holds no lock past its own statement (the cycle `FOR SHARE` of `assertCycleOpen` runs on the pool, so it lasts one statement, `timelines.service.ts:442-445`) and opens no transaction, so a refusal writes nothing (no audit row, no `markExecuted`). A no-op (`diffTimeline` is `{}`) answers the stored timeline, no version bump, no audit row, no `markExecuted`. Neither is invisible to the key: see *Idempotency* below. The clock is read once per request (`ADMIN_CONFIG_CLOCK`): the same `now` judges the rules, stamps `updated_at` and the audit row, and reads the answer. Locks (`checkLocks` in `timeline-rules.ts`) judge **changed** fields only, from `viewTimeline` over the stored steps: a `closed` step's dates are `LOCKED`; an `in_progress` step's `opensOn` is `LOCKED` and its `closesOn` cannot go before today (`BEFORE_TODAY`); an `upcoming` step's `opensOn` cannot move before today; a scope change is `LOCKED` (on `programIds` / `resultTypeKeys`) once step 1 is not `upcoming` or the timeline has a load. Scope merge (`mergeScope`): a flag turned on with no list empties the list; a list without its flag is judged against the stored flag; a catalog is read only when an explicit list changes.
- **The hold (FR-6, DD-2).** In `viewTimeline`: step 1 exists, its `opensOn` is today or earlier, and `hasLoad` is false gives status `waiting_for_load`; it wins over the dates (even after every `closesOn`): every step is `upcoming`, `currentStep` is `null`, `nextStep` is 1. A hold therefore asks for no in-progress confirmation and leaves the scope open. Until loads exist every timeline whose step 1 has opened is on hold. Open question OQ-TE-1 (`timeline-edit/requirements.md` § 9): a hold edit may move step 1's close into the past (FR-3 allows it).
- **Loads port (NFR-6, DD-3).** `TIMELINE_LOADS` (`timeline-loads.ts`): `withLoad(timelineIds): Promise<ReadonlySet<number>>`, one batched call per read. Bound in `timelines.module.ts` to `NoTimelineLoads` (an empty set, **no query**). **P2-3905 swaps that one provider** for a query over `timeline_loads`; the view and the rules do not change. Two things that story must handle: (1) the edit reads `hasLoad` **before** the transaction (`update`, step 2) and does not re-check it under the lock, so when real loads land either re-read it under the timeline lock or have a load bump `timelines.version`; (2) it adds one query to the list (the count goes from six to seven, the test names the port).
- **Edit audit.** One row in `timeline_audit_events` per applied edit, inserted in the edit's transaction (`insertAuditEvent`), never for a refusal or a no-op: `timeline_id`, `actor_id`, `action` (`update`), `changes` (`{ field: { before, after } }`; keys `name`, `allPrograms`, `programIds`, `allResultTypes`, `resultTypeKeys`, `steps.<position>.<name|opensOn|closesOn>`, lists sorted), `request_id`, `created_at`. Append-only (no update columns). Both foreign keys are `ON DELETE no action`: a future timeline or user delete must remove or keep the audit rows first. `timelines` gained `version` (starts at 1, +1 per applied edit; assigns and removes do not bump it), `updated_at`, `updated_by` (set together or both null, `chk_timelines_updated`), migration `0004`.
- **Closed cycle:** timelines and assignments cannot be written in a `closed` cycle (409 `CYCLES_CLOSED`). Reads work in any status.
- **No PII in logs (NFR-7).** One `event: 'admin_config'` line per write: `action` (`cycle_create`, `cycle_activate`, `timeline_create`, `timeline_update`, `timeline_user_assign`, `timeline_user_remove`, `field_config_update`, `field_config_discard`, `field_config_publish`), `targetId`, `actorId`, `outcome`, `reason?`, `requestId`, `idempotency`. Never a name, email or body. A user's email appears only in the `TimelineDetail` response, which is ADMIN-only; do not copy `TimelineUserResponse` into another endpoint (FR-12 of *user-management*: other endpoints use `toPublicUser`).
- **Reads cost a fixed number of queries (NFR-5):** the timeline list runs six queries whatever the number of timelines (cycle, timelines, then steps, programs, result types and assignment counts by the listed ids). The loads port adds none while `NoTimelineLoads` is bound; a real adapter makes it seven (one batched call, never one per timeline). Do not add a per-timeline query; the fake store counts calls and a test pins it.

## Field configuration (`field-config/`)

Which fields QA shows, per cycle and result type: a **draft** the ADMIN edits, and **immutable versions** published from it. Spec: `docs/specs/archive/2026-10-27-admin-config--field-configuration/` (`design.md` DD-1 to DD-12). A timeline uses a version by its start date, never by editing it. `FieldConfigModule` (`field-config.module.ts`) is its own Nest module so its replay reader answers a publication. Its **only export** is `FIELD_CONFIG_EFFECTIVE` (`field-config.module.ts:31, 95`), the port later review stories inject: `effectiveFor(cycleId, timelineId, resultTypeKey)`.

|---|---|

| `field-config.service.ts` | `view`, `preview`, `updateDraft`, `discardDraft`, `publish`, `replayPublish`, `effectiveFor`; `FieldConfigBusyError`; one `logged()` line per write |
| `field-config-rules.ts` | Pure `validateDraftEdit`: `INVALID` and `NOT_ASSESSED`, every problem at once, paths `items[i].<field>` |

| `field-config-versions.ts` | Pure `versionFor` and `receiveAndKeep` (the version rule) |

**Tables (migration `0005_field_configuration.sql`):** `field_config_drafts` (one row per cycle: `revision`, `updated_at/by`; created by the first draft write, so a cycle with no row reads revision 0), `field_config_draft_items`, `field_config_versions` (unique `cycle_id` + `number`; `published_at` a whole-second `datetime`), `field_config_version_items`, and `field_config_audit_events` (**one row per publication**, unique `version_id`, `changes` and `timelines` JSON). Append-only audit; only publications are audited, draft edits are not.

**Rules**

- **Lock order (DD-6):** cycle row `FOR SHARE` (closed re-checked under it), then the draft row `FOR UPDATE` (`lockCycleShared`, `ensureDraft` then `lockDraft` for an edit, `field-config.store.ts:364-390`). Readers never lock. The publish and the discard hold the same two locks, so they serialize with a draft edit.
- **The database decides a race (DD-6).** `bumpRevision` is a conditional `UPDATE ... WHERE cycle_id = ? AND revision = ?` (`field-config.store.ts:412-440`, the WHERE at `:430-437`); 0 rows is 409 `FIELD_CONFIG_REVISION_STALE`. An edit and a discard pass no expected revision and always win. A duplicate (`cycle_id`, `number`) on the version insert is the same stale 409 (`field-config.service.ts:564-566`). No retry.
- **The revision moves** on every applied edit, discard and publish (a publish leaves `updated_*` as the last draft write set them).
- **Version rule (DD-5, `versionFor`, `field-config-versions.ts:96-117`):** a version counts for a started timeline when the Rome date of its `published_at` is **before** step 1's `opensOn`; one published on the opening day does not. A started timeline resolves to the latest counting version or to `'none'` (never a fallback); a timeline not started resolves to the latest version, provisional. Started means 00:00 Rome on `opensOn`, also on hold. **A publication reaches only timelines that have not started.**
- **Whole second (DD-5):** the service cuts the clock to the second (`wholeSecond`, `:157`), so the instant judged, stored and answered is one value.
- **Reads before the transaction (DD-7, DD-8a):** the diff, the version rows and the receive / keep lists are computed from data read before the transaction, with the one clock reading; the audit row records those lists (ids and version numbers), which the replay returns.
- **S-14:** a flag left out of an edit item is stored `false`, also on `assessed`. `isCore` / `isAiInput` true on a non-assessed field is `NOT_ASSESSED` (a field code, `error-codes.ts:357`).
- **Catalog per cycle year (DD-4):** a missing catalog is 409, an unreachable or malformed one is 503, never an empty list. `is_new` must be a boolean or absent (else 503).
- **Busy (T-7):** a write that loses a lock (1213 / 1205) is 503 `SERVICE_UNAVAILABLE` via `FieldConfigBusyError`, nothing committed, rethrown and never retried here (`:674-683`).
- **Idempotency:** only the publish is keyed. It marks the key in its transaction (`markExecuted`) and stores the **version id** in `idempotency_keys.target_user_id`; the module's replay reader (`field-config.module.ts:87-92`) calls `replayPublish(versionId)`, which returns the lists as recorded and joins names and `opensOn` from the timelines **now** (a deleted timeline reads `name: ''`, `opensOn: null`).
- **Verified on MySQL (T-11, TEST, 2026-10-26):** five overlapping publishes of the same revision gave one 201 and four 409 `FIELD_CONFIG_REVISION_STALE`, one version and one audit row. `published_at` is stored to the whole second.
- **Open finding:** the first view of a year whose catalog is not cached yet hung for more than 45 s on TEST instead of failing with 503 within 10 s (NFR-6); later calls answered in under 0.3 s. Unit tests at `/akili-test` (`reporting-qa-catalog.client.spec.ts`, *NFR-6: a hung Reporting…*) show the client ends every path it controls at 10 s (no headers, a stalled body, joined requests), so the cause is outside the client: the TEST proxy, DNS/TLS, or something before the controller. Read the TEST server logs before trusting the bound end to end.
- **Known limits:** `upsertDraftItems` uses `VALUES()`, deprecated since MySQL 8.0.20 (`field-config.store.ts:397`). A no-op edit answers from an unlocked read, so it can show a slightly stale draft.

## Idempotency

`POST /cycles`, `POST /cycles/:id/timelines`, `PATCH /timelines/:id` and `POST /cycles/:id/field-config/publish` (see *Field configuration*) are `@Idempotent()` (FR-17; timeline-edit FR-13). The edit marks its key in the edit's transaction (`markExecuted`); a refusal or no-op marks nothing, **but the interceptor still stores the answer under the key**: every 4xx refusal (DD-5, `idempotency.interceptor.ts:103-112, 309-322`) and the no-op 200 are saved as the key's answer and replayed as they were (same status, code and `fields`, `Idempotency-Replayed: true`); only a 5xx or an unknown failure frees the key. The fingerprint covers method, path and canonical body (`fingerprint.ts`, compared at `interceptor.ts:227`), so a same-key request with another body is 422 `IDEMPOTENCY_KEY_REUSED`. Two consequences: (1) a replay of an **applied** edit (the stored 200, or the crash window below) never answers 409 stale (FR-13), but a first 409 stale or unconfirmed replays as that 409 (`admin-config-timelines.e2e-spec.ts:2697-2718`); (2) a confirmed resend (`confirmInProgress: true` changes the body) and any redo after a stale reload need a **fresh** key. The crash window (committed, answer not stored) replays through the same reader, which re-reads the timeline **as it is now** (DD-9). The mechanism is `src/common/idempotency/` unchanged; each module binds `IDEMPOTENCY_STORE`, `IDEMPOTENCY_CLOCK` and its own `IDEMPOTENCY_REPLAY_READER`. The stored target id sits in the column named `idempotency_keys.target_user_id` (a historical name; no foreign key): it holds a **cycle id** for `POST /cycles`, a **timeline id** for `POST /cycles/:id/timelines` and for `PATCH /timelines/:id`, and a **version id** for `POST /cycles/:id/field-config/publish`. Each replay reader knows which one it has and re-reads the cycle, the timeline or the publication. Assign, remove and activate take no key: they are naturally repeat-safe (assign answers 200 for an existing row; activate answers 409 for an already active cycle; remove answers 404 the second time).

## Reserved tables (NFR-6)

`timeline_loads` and `timeline_results` are **not created** by migration `0003`. They are reserved for the load stories (P2-3905, P2-3906): `timeline_loads` hangs from `timeline_id` + `timeline_step_id`, `timeline_results` from `timeline_id` + `result_id` + `load_id`. Nothing in the six tables needs to change for them. Readiness already lists `NO_RESULTS_LOADED` for every timeline until they exist; later work adds items without changing the existing ones. Only the loads port (`TIMELINE_LOADS`) exists in front of them; see *Loads port* above. The visibility predicate for assessors (P2-3909) and the result filter are **not built** here (editing steps, P2-3904, is built: spec `timeline-edit`).
